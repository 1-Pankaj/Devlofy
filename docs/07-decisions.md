# Decision log (ADRs)

Format: **decision → why → consequences**. Newest at the bottom. Superseding a decision appends, never rewrites.

## ADR-001 · Feature budget rule
**Decision:** every accepted feature displaces an existing one or goes to [[08-backlog]].
**Why:** solo dev, limited hours; scope creep is the project killer.
**Consequence:** saying yes requires saying no out loud.

## ADR-002 · No backend, no cloud AI
**Decision:** local SQLite is the entire backend. "AI" = local rules/scoring/algorithms, explicitly never a chat.
**Why:** privacy, zero cost, works on a plane, no ops burden.
**Consequence:** sync/multi-device is explicitly unsolved (accepted); export/backup is mandatory from v0.1.

## ADR-003 · Web-first, then Android native; tablets as first-class
**Decision (updated 2026-10-17):** Web stable + **Android native primary** (phones *and tablets*, desktop mode in v0.1). iOS later.
**Why:** user has an iPhone but no MacBook; Android hardware is immediately testable; web gives day-one reach and a PWA dogfood path.
**Consequence:** platform adapters are mandatory (`feature.native.ts` / `feature.web.ts`); nothing imports platform-only libs in core code.

## ADR-004 · Custom design system over component kits
**Decision:** brand system "Ink & Sprout" built on tokens + owned primitives (Panel, AppButton, AppText, …). No React Native Paper / RNUILib.
**Why:** kits ship generic Material/iOS looks; the user explicitly wants a rich, non-generic, native-feel identity. Paper was installed early and removed.
**Consequence:** we own more components; every new component must go through `src/theme` tokens.

## ADR-005 · Fonts & icon set
**Decision:** Geist (UI) + Space Grotesk (display) + JetBrains Mono (machine), Phosphor icons (light/regular weight).
**Why:** taste-skill banned Inter/Roboto and stock thick icon sets; these read as precise developer tools and work offline (bundled).
**Consequence:** font weights are separate static files; styles never set `fontWeight`.

## ADR-006 · Plain SQL repos over an ORM
**Decision:** `src/lib/db/repo.ts` with typed `getAllAsync/getFirstAsync/runAsync` + hand-written migrations (no Drizzle/Prisma).
**Why:** the ORM expo driver is historically sync-API oriented; web wasm constraints (sync API, FTS absence) make hand-rolled SQL the safe path. Screens consume typed functions either way.
**Consequence:** schema changes touch migration + repo + [[06-data-model]]. Tooling (drizzle-kit) is unnecessary.

## ADR-007 · Procedural 3D first, Blender GLBs layered in
**Decision:** the garden ships as deterministic procedural geometry; Blender assets replace/extend it later without changing the scene API.
**Why:** 3D from day one without asset-pipeline risk; keeps the app shippable while Blender sessions are intermittent.
**Consequence:** `garden-scene.tsx` must keep `(seed, growth)` props and a procedural fallback forever ([[05-blender-pipeline]]).

## ADR-008 · One R3F scene, two runtimes via a shim
**Decision:** `@/lib/three` resolves `@react-three/fiber/native` (expo-gl) or web per platform; scene code imports only the shim.
**Why:** avoids duplicated scenes; keeps the adapter rule (ADR-003) intact; web honors the same code path as Android.
**Consequence:** platform-specific three imports anywhere outside the shim are forbidden.

## ADR-009 · Navigation architecture (floating bar ⇄ side rail)
**Decision:** custom `FloatingTabBar` on compact widths; `DesktopShell` side rail in desktop mode; no native `NativeTabs` (template default was replaced).
**Why:** brandable icons/states across Android + web, and the rail requirement can't be met by stock tab bars. Tab switches don't animate.
**Consequence:** `useDesktopMode()` gates layout; switching modes remounts the navigator (accepted for now).

## ADR-010 · Reanimated 4 compiler-safe API
**Decision:** shared values use `.get()` / `.set()`; React Compiler experiment stays enabled; no `runOnJS` (use `scheduleOnRN` from `react-native-worklets`).
**Why:** RN 0.88 + Reanimated 4 + compiler enabled in the template; `.value` assignment fails lint immutability checks and risks compiler mis-optimization.
**Consequence:** any animation PR must pass `npx eslint .` with the immutability rule on.

## ADR-011 · Zustand persist via platform storage adapters
**Decision:** settings persist through `createJSONStorage(() => kv)` where `kv` is `expo-sqlite/kv-store` on native and `localStorage` on web. Zustand stays out of the database.
**Why:** settings aren't syncable user content; they're cheap, local, and must load before the DB opens.
**Consequence:** new persisted stores must use `src/lib/storage`, not direct platform APIs.

## ADR-012 · Garden models: Blender GLBs over the procedural fallback
**Decision:** the garden prefers one Blender-authored GLB per growth stage (five stages, seed → canopy, in `assets/models/`); the procedural tree remains the loading state and the permanent failure fallback.
**Why:** authored geometry reads better than recursion, while the fallback guarantees 3D from the first frame on any device and keeps the app shippable if loading ever breaks.
**Consequence:** new stages/props ship as GLBs plus an entry in `src/lib/garden/models.ts`; loading stays behind `src/lib/three/load-model.*` (ADR-008), and failure must never blank the scene.

## ADR-013 · Design language "Daylight" (supersedes the Ink & Sprout look)
**Decision:** the surface system moves from OLED ink + neon sprout to a neutral, light-first palette. Light is paper (`#F5F6F8` canvas, white cards); dark is neutral charcoal (`#0F1115`), never pure black and never colour-cast. One deep emerald accent (the sprout survives, the neon does not). Conventional radii (6–20 instead of 10–28), quiet two-step elevation, text-first hierarchy, and **one type voice** — Geist for everything, JetBrains Mono only for code and tabular figures. The Double-Bezel card becomes a single bordered surface, the ambient `Glow` component is deleted, and compact widths get a solid, edge-anchored `BottomTabBar` instead of the floating pill.
**Why:** the previous system read as a high-end/AI demo rather than a product: neon-on-near-black with a green cast, mono uppercase eyebrows as the signature motif, oversized squircles, machined "bezel" shells, and glow blobs on every dark screen — with very low information density. The stated reference set is mainstream product design (Instagram / WhatsApp / Facebook / LinkedIn): neutral surfaces, familiar navigation, one accent used sparingly, and screens that carry real information.
**Consequence:** supersedes the palette/typography parts of ADR-004 and ADR-005 and the compact-nav half of ADR-009. `Glow` and `FloatingTabBar` are deleted; `BottomTabBar` renders in the layout flow. Nothing is reintroduced without a new ADR. ADR-004's core (own the primitives, no component kit), ADR-005's Phosphor decision, and ADR-009's side rail all stand. New surfaces must be built from `src/theme` tokens — no hardcoded colour, radius, font size, or shadow.

## ADR-014 · Design language "Material 3 Expressive" (supersedes ADR-013's palette, surfaces, shape and gradient rule)
**Decision:** Devlofy adopts **Material 3** as its design system and works in its *Expressive* register. A **tonal** scheme replaced the light-first neutral palette: `background #F5F2FB` / `surface #FFFFFF` in light and `#131318` / `#1F1F26` in dark, with an **indigo** primary (`#4B5AA0` / `#BCC2FF`) and an **amber** tertiary (`#A85A08` / `#FFB870`) reserved for focus and time. Surfaces separate by **tone, not borders** — the 1px grey outline is gone from every container (`Panel` is filled/elevated/outlined, default filled). The shape scale is Material's (4/8/12/16/28/full) and buttons, chips and the FAB are pills. Every tab screen carries exactly **one extended FAB** (`Fab`) as its single action — Today `Start focus`, Garden `Focus for 25m`, Work `New project`, Notes `New note` — and nothing else on those screens is filled. The gradient system is deleted (`GradientSurface` removed, `ProgressRing` lost `gradientTo`): a colour block is a colour, not a blend. Type grew (display 34 / title 24) and entrances are springy. Segmented controls gained a check mark so selection never relies on colour alone.
**Why:** the Daylight pass was judged a re-paint, not a redesign — it changed hue while keeping one bordered white card stacked on another, so dark mode looked like the previous build. The complaint was structural. A tonal surface hierarchy, one floating action per screen, and asymmetric bento layouts change the *composition* of every screen, not just its colour. Indigo was chosen over the previous green and the interim berry because the garden owns green, the user rejected pink, and amber-for-time keeps "focus" legible as a second, meaningful hue.
**Consequence:** supersedes ADR-013's palette, surface treatment, radii and gradient rule; ADR-013's navigation, primitive-ownership, Phosphor and side-rail decisions stand. Gradients may only return with a new ADR. New surfaces must be `Panel` variants or `accentSoft`/`emberSoft` blocks built from `src/theme` tokens. [[04-design-language]] is the canon.


## ADR-015 · Precise motion, and a v0.2 feature batch the schema already allowed
**Decision:** two things at once, because they answer the same feedback ("the animations feel wrong, give me more that's useful").
1. **Motion is precise, never playful.** Every spring with `dampingRatio < 1` and every `springify()` is removed. Springs survive only as **critically damped** (`spring.settle` 300, `spring.precise` 220); everything else is a timing curve (`easing.out`, `emphasized`, `inOut`, `sheet`) over the five `duration` steps. Press feedback is symmetric timing in/out at 0.975, `FadeUp` is a timed 8 px rise, the nav pill slides on Material's emphasized curve, and `LiveDot` breathes over 1600 ms instead of blinking.
2. **Five features, no migrations.** The v1 schema already carried `sessions.project_id`, `tasks.est_minutes`, `tasks.priority` and `tasks.due_at` unused, so the working day was built on data the app was already storing: project attribution for focus blocks (persisted selection in settings, `project_name` joined onto sessions, tracked minutes per project on Work and the project page), a **twelve-week rhythm heatmap** on Garden, a **daily focus goal** in More that drives the ring and the heatmap bands, a **quick-add grammar** (`!3 45m tomorrow #Northwind`) with a live parse preview, and a **due-date-ordered day queue** with due pills.
**Why:** motion with overshoot reads as a toy on a tool you sit inside for hours; a short rise and a fast settle reads as precision. And the fastest useful features are the ones the schema already pays for — attribution is what turns a timer into "this project cost 14 h 20 m", which is the question a freelancer actually asks. Every addition is local, offline and deterministic ([[01-vision]]), so none of them weakens the no-backend promise.
**Consequence:** the feature-budget rule in [[AGENTS]] was **explicitly overridden by the user request** for this batch rather than applied; the displaced work (energy pairing, manual reordering, due-date editing after creation, command palette) is written into [[02-scope]] v1 and [[08-backlog]] instead. `parse-task.ts` is pure and unit-testable — the grammar is the contract, so extending it means extending its header comment and the preview together. No schema change was needed, so [[06-data-model]] stands.
**Amended (2026-10-19, the ADR-022 audit pass):** the two **spring tokens were deleted, not merely damped.** Nothing in the app ever animated on a spring, so `theme/motion` now exports the five `duration` steps and exactly two curves (`easing.out`, `easing.emphasized` — the unused `inOut` and `sheet` went with them). The rule is stronger than it was: there is no spring at all rather than a well-behaved one.

## ADR-016 · The Engine is a pure, deterministic ranking — no model, no server
**Decision:** `src/lib/engine/` is Devlofy's intelligence layer, and it is **pure functions over the user's own rows**: `rhythm.ts` (focus minutes bucketed by local hour and weekday, the contiguous 3-hour peak band, the median block length, and the sentences the UI may show), `next-up.ts` (a documented weight table that scores every open task and returns the *reasons* it scored that way), `estimate.ts` (estimated vs actually-focused minutes per task → a drift ratio). `use-engine.ts` wires those to `useLiveQuery` so Today and Garden read the same numbers. The "Next up" card on Today names one task, shows up to three reasons as pills, and offers **Focus on this** (which starts a block attributed to the *task*, not just the project) and **Show me another** (a local, cheap override).
**Why:** the product's stated edge is local intelligence ([[01-vision]], [[03-architecture]]), and the strongest version of it needs no network at all: the app already knows what you said matters (tasks: priority, due, estimate, energy), what you actually did (sessions: minutes, hour, attribution) and where the time went (projects). "You plan 70m, it takes 82m" and "your strongest stretch is 09:00–12:00" are facts a to-do list cannot produce, and they are only possible because earlier versions prompted for that data. A recommendation that cannot state its reason is not allowed here — if the card ever says "do this" without a why, it is a bug in `next-up.ts`.
**Consequence:** the Engine has no thresholds tuned to a demo and no hidden randomness; weights live in one `WEIGHT` table so they can be argued with. It stays silent rather than inventing patterns (`MIN_SESSIONS_FOR_INSIGHTS = 6`, drift needs 4 samples). The v3 vision of *optional tiny on-device models* stays in [[02-scope]] behind a flag — this ADR ships the deterministic core and forbids reaching for a model to solve what a rule can.

## ADR-017 · Money: rates on the project, bills as views, no invoice table
**Decision:** migration **v2** adds `hourly_rate` to `clients` and `projects` (append-only `ALTER TABLE`). A block's rate resolves as `COALESCE(projects.hourly_rate, clients.hourly_rate)`; a project rate wins, the client's is the inherited default. `startFocusSession()` resolves that rate at start and marks the block **billable** when a rate exists, so pricing is automatic from the moment the work happens. `/invoice` is a screen, not a stored document: it picks a period (this month / 30 days / this week / all time) or one client, groups billable blocks into line items, and recomputes every time — including the "copy as text" export (`src/lib/money.ts` is pure).
**Why:** a stored invoice can disagree with the time log it came from; a *view* cannot. Rates are the only new user input, and putting them where the work is (a project, or a client for all of theirs) means they are typed once, not per block. The default-on billability matters more than a per-session toggle: for a freelancer, "time on a client project is billable" is the sane assumption, and the screen lets you take any single block off the bill with a tap.
**Consequence:** money is presented in **accent** (brand), not ember — ember stays reserved for focus/time ([[04-design-language]]). The currency symbol is a setting (`CURRENCY_OPTIONS`), shown with its picker on the invoice screen where the question first arises; the app never guesses a currency. Time on projects with no rate is surfaced honestly ("2h 47m cannot be billed") instead of silently priced at zero. A real invoice entity (numbering, sent/draft state, PDF) remains v2 scope in [[02-scope]].

## ADR-018 · Search: one screen over four kinds, LIKE in both runtimes, ⌘K on web
**Decision:** `searchEverything()` runs four bounded `LIKE` queries (projects, clients, notes, tasks) and returns them as one grouped result set on `/search`, reachable from the Today header and from **Cmd/Ctrl-K on web** via a platform adapter (`src/lib/search-shortcut.ts` + `.web.ts`, the native side a deliberate no-op). Projects, clients and notes navigate to their detail routes; a task row toggles completion in place (its trailing slot shows the state, not a caret) so no result is a dead end.
**Why:** in an app that owns all your data, "where did I put that?" is the most common navigation problem, and the answer usually arrives when you guess the wrong noun — searching one kind at a time forces you to guess right. LIKE rather than FTS5 because the same code path has to run on the wasm web build ([[03-architecture]]); for personal-sized datasets it is instant either way. The shortcut is web-only because native has no global key handler, and pretending otherwise would ship a broken affordance.
**Consequence:** FTS5 on native stays a v1.5 optimisation behind a capability check ([[06-data-model]]); if it lands, it must return the same shape. Result growth needs `LIMIT` discipline per kind. Any new entity type (milestones, clients' contacts) is added to `GROUPS` in one place.

## ADR-019 · GitHub: two ways in, one read-only snapshot with a date on it
**Decision:** `/github` (from Work, and the only screen in the app that needs the network) shows what is **waiting on the user**: pull requests with a review requested from them, their own open pull requests, issues assigned to them, the newest CI run on each of the most recently pushed repos, and those repos. It is **read-only** — the app never issues a write to GitHub. Authentication has two doors to one connection: a **pasted token** (both platforms, needs nothing from GitHub's app registry) and the **device flow** (Android only, enabled only when `expo.extra.githubClientId` in `app.json` is set). The token lives in the KV adapter (`src/lib/storage`), not the OS keychain, and connecting *proves* the token against `/user` first, so a bad token is never stored. The last good response is cached in KV as a **snapshot with `fetchedAt`**; opening the screen paints it immediately, a background refresh runs only if it is older than 10 minutes, and a failed refresh **keeps the snapshot** and adds a sentence saying so.
**Why:** every other part of this app works on the device, so the code host is the one place freshness cannot be assumed — which is an argument for making staleness *visible* rather than hiding it behind an empty state. Two doors exist because the platform decides the grant: the standard web flow needs a callback URL that a serverless app cannot provide, and the device flow cannot run in a browser at all — `github.com/login/device/code` and `/login/oauth/access_token` send **no CORS headers** (verified by hand; `api.github.com` does, so reads work on web). A pasted token is therefore the honest web path, and the only path when no client ID is configured. Read-only because a dashboard should not be able to break the thing it reports on.
**Consequence:** permissions are per-token, so a section may legitimately fail while the rest succeeds: each section is fetched independently and a failure becomes a line in `notes` ("Checks: … this token cannot read Actions"), never a silently empty list and never a blank screen. The absent-keychain choice is deliberate (no new dependency, cannot break Expo Go) and the UI says where the token is and offers to forget it; `expo-secure-store` (Android Keystore) is in [[08-backlog]] and needs a dev-build check. Nothing here touches SQLite: the cache is a KV value, keeping the database the home of user content only (ADR-011). Unauthenticated network calls stay confined to `src/lib/github/`.
**Amended by ADR-020 (v0.5):** the **read-only rule only** is superseded — GitHub is now two-way, bounded by a branch rule that makes the original objection structurally impossible rather than merely forbidden. Everything else above stands unchanged and still governs: two doors in, the token proved against `/user` before it is stored, the KV snapshot with `fetchedAt`, the background refresh only when older than ten minutes, a failed refresh that keeps the snapshot and says how old it is, and per-section failure as a sentence. (The `expo-secure-store` note is now known to be cheaper than stated — it ships in Expo Go — see [[09-platform-ceiling]].)

## ADR-020 · GitHub two-way: writes only ever land on a branch, never on the default one
**Decision:** `/github` becomes the whole code host, not a window onto it — browse and read with syntax highlighting, edit a file and commit, open a pull request, review it (approve / request changes / comment), merge it (merge / squash / rebase), file and triage issues, control Actions (dispatch runs with typed inputs, re-run, cancel), publish a release from GitHub's own generated notes, and read the notification inbox. This reverses ADR-019's read-only rule, so it replaces that rule with a **write-safety contract** that the code, not the user, is responsible for:
1. **Never the default branch.** There is no code path that commits to it. An edit either appends to an existing non-default branch or creates one; the default branch is read-only by construction, and `commitFile`/`commitFiles` are only ever reached with a branch the editor just created or selected.
2. **Branch → pull request, never straight to `main`.** A commit is followed by an offer to open the PR in the same flow, and the PR screen is the same screen that reads one.
3. **The diff comes first.** The editor shows the change against the blob's `sha` before the button that commits it, and the button states its consequence ("Commit to `devlofy/fix-typos`"), not "Save".
4. **No force, no deletion.** The Git Data ref update is a plain `PATCH` with no `force`; a branch that moved while the editor was open is refused (422) rather than overwritten. There is no branch deletion and no repository deletion in the app at all.
5. **Stale writes fail loudly.** An edit carries the blob `sha` it read, so GitHub's own `409` catches the case where someone else committed in the meantime — and the screen says so in words instead of retrying.
**Why:** the original objection — "a dashboard should not be able to break the thing it reports on" — is still right; the answer is not to stay read-only but to make the dangerous operations *structurally* unreachable. A solo dev on a tablet wants to fix a typo, land it on a branch, and review it, without the possibility of a mistaken push to `main`; those wants and that safety are compatible if the branch rule lives in the module rather than in the user's discipline. The same reasoning keeps the write surface bounded: no merges outside the PR endpoint, no repo settings, no branch delete, no force-push — every write is one of nine documented endpoints ([[09-platform-ceiling]]).
**Consequence:** GitHub is no longer "read-only", so the read-only wording is gone from the Work row, the tokens, and the docs; the network row in [[03-architecture]] changes from "read-only" to "two-way, branch-bounded". The device-flow token is a *classic* `repo` token and therefore can write — the connect screen says that out loud, and a pasted fine-grained token with `Contents: Read` remains the least-privilege way to browse. ADR-019 stands for everything it said about **authentication, caching and per-section failure**: two doors, the KV snapshot with a date on it, and a failed refresh that keeps the old data and says how old it is. Writes are executed against GitHub directly (no local clone), so a commit *is* a push; that is why the diff-before-commit step is not decoration. Continues to touch no SQLite: unauthored GitHub data stays in KV (ADR-011).

## ADR-021 · Bench: the offline toolbox is pure logic plus one host screen, and snippets are user content
**Decision:** Devlofy gains its first new **category** since v0.1 — **Bench**, a shelf of eleven everyday developer tools — and it gains it with three structural choices:
1. **It lives in More, not a sixth tab.** `/bench` is a stack with a shelf (`index`), one host route (`[tool]`), and the kept-snippets list (`snippets`). The tab bar keeps its five destinations; Bench is reached from a section on More the way settings are, because it is a place you visit with an errand, not a place the app's day runs through.
2. **Pure logic outside the screen, verified by known-answer checks.** Every tool's work is a pure function in `src/lib/bench/*` (`hash`, `json`, `sql`, `regex`, `jwt`, `encode`, `time`, `colour`, `patch`, `textstats`, `tools`), and `src/lib/bench/self-check.ts` holds **80 known-answer assertions** over them — published SHA-1/SHA-256 vectors, RFC semantics for base64/URL/JWT, cron expressions resolved against real timestamps, contrast ratios, and diff/patch round-trips. It runs in Node against the TypeScript as-is (`npx tsc … --outDir /tmp && node -e "require('…self-check').runSelfCheck()"`), unit tests without a test runner, on a project where adding vitest was not worth a dependency. Every tool computes **as you type** — there is no Run button to press and no state that can disagree with the input.
3. **Snippets are user content, so they go in SQLite.** Migration **v3** adds `bench_snippets` (id, tool, title, body, language, `created_at`, `updated_at`, `deleted_at`) — a real table, not a KV value, because a snippet has a title, a tool it belongs to, an edit history worth keeping and a tombstone worth honouring, and because it must appear in the app's own JSON export ([[06-data-model]]).

Two smaller rules that came out of building it, both now house rules:
- **The value you save is the tool's own artifact** — the formatted document, the unified patch, the regex, the digest, the cron expression — and opening a snippet **re-opens it in the tool that made it** (`/bench/<tool>?snippet=<id>`), with delete living in the panel that owns the snippet's identity. This is the note-editor pattern ([[04-design-language]]): you open the thing, then act on it.
- **A pressable row's trailing slot is never interactive.** `ListRow` is itself a button, so a button inside it is invalid HTML on web and ambiguous to a screen reader. Delete therefore never appears in a snippet row; it is a two-tap confirm on the screen where the snippet is open (the same fix the GitHub hub made for its private pill).

**Why:** "a toolbox" is where an offline-first app either tells the truth or starts lying. The lie is a YAML/XML "formatter" that half-parses, or a hash tool whose SHA-1 disagrees with `git` — so v1 ships eleven tools that each do one thing *correctly* and drops the two the schema could not honestly support. The known-answer harness is the reason that claim is checkable rather than asserted: it caught four real bugs while this shipped (a rotate in SHA-1's `rotr(b,2)`, a missing `rotl(…,1)` in the message schedule, a bad `rotr`/`rotl` mix in the round function, and a JSON error offset that Hermes and modern V8 refuse to give, now computed by the app's own validator so "Line 3, column 1" is true on Android as well as web), and it caught a **pre-existing** one in ADR-020's shared `diffLines`: `pushContext` indexed context text as `prefix + k`, so every diff whose two sides share a leading line — most real diffs — printed the wrong line as context in the GitHub editor too. Bench inherits that fix, and the fix is now covered by three checks.

**What Bench reuses rather than reinvents:** the app's own highlighter (`src/lib/highlight.ts`) for the code views, `src/lib/diff.ts` + `src/lib/bench/patch.ts` for the diff and the paste-able unified patch, `src/lib/base64.ts` and the KV-free hash layer for digests — all previously built for GitHub, now shared. **No new dependency was added**, and nothing in Bench touches the network: the whole category runs on the device, which is why it works in Expo Go on both platforms.

**Consequence:** the deferred HTTP/API client (saved requests, environments, an honest CORS story on web) stays Bench's **second** release in [[08-backlog]], because it is the one part that needs the network path. `searchEverything()` still covers four kinds and does **not** include snippets: a snippet is a value you go and use, and it has its own search on `/bench/snippets`. `hunkHeader()` in `src/lib/diff.ts` is now the single spelling of a hunk header for both the rendered diff and the patch text, so the two can no longer disagree (the abbreviated `@@ -1 +1 @@` was wrong whenever a side contributed more than one line). The self-check harness is the pattern for the rest of the pure modules — "unit tests" in [[08-backlog]] now means extending an existing file, not standing up a runner.

## ADR-022 · The 3D kit has two authoring paths, and a model you cannot look at is not verified
**Decision:** the Focus Garden gains a **code-authored prop kit** (`src/lib/three/kit/`) beside the Blender GLBs, and a **software renderer** (`tools/preview/`) that draws it without a GPU. Concretely:
1. **A placement is answered by an authored GLB or by the kit — never by nothing.** `src/lib/garden/props.ts` resolves every prop through a small mapping: the two props with **no** authored model (`bench`, `signpost`) are always built in code, every other prop prefers its GLB and falls back to the code model if that GLB never arrives, and an earned trophy with no GLB waits rather than showing a stand-in that would teach the wrong shape.
2. **The kit is code, not assets, on purpose.** It needs no Blender session, no fetch and no parse — it builds synchronously on the first frame — which is what makes it usable as the fallback and makes it the only way to author a *new* prop in an environment without Blender. It is not a replacement: the GLBs remain the preferred read, and ADR-012's procedural tree remains the tree's fallback.
3. **Two of the props are data.** This is what stops the kit being decoration: `bench` unlocks with growth, and `signpost` hangs **one plate per active project** (`countActiveProjects()` → `dressingFor(growth, projects)`). That was [[05-blender-pipeline]]'s own open backlog item, and it needed a shape that no static asset could have given it.
4. **The kit is verified by a renderer, not by a screenshot.** A browser without a WebGL context — which is what a headless container gives, and what the app itself must survive — can only show the "3D is unavailable" still. So the tool **builds every variant, checks its invariants** (finite vertices, base at y = 0, sane height and footprint, a ≤700-triangle budget, determinism by rebuilding and comparing, exactly one glow mesh on the lantern, a consumer in `props.ts` for every model) **and software-rasterises a contact sheet** to a PNG with the scene's own lights and the same linear→sRGB conversion.
5. **The coverage rule is compile-time.** `props.ts` types its two maps so a hole cannot be expressed: `Record<GlbProp, GltfAssetModule>` demands a module for every authored prop, `Record<KitProp, KitAnswer>` demands a kit entry for every prop without one. Adding a prop to either union without an answer fails `npx tsc --noEmit` rather than rendering an empty clearing.

**Why:** three separate problems turned out to have one answer. The first was **availability**: the GLBs come from a live Blender session, and without it the garden was frozen — the app shipped a 3D scene that could not gain a single object. The second was **data**: a bench and a signpost-with-notches are shapes that *express state*, and a static GLB can only express the state it was authored in. The third was **verification**: `expo export` proves a bundle builds, `tsc` proves types line up, and neither can tell you whether a bench looks like a bench. A GPU-less rasteriser over the app's own geometry answers that last question in about a second, in the repo, with no test runner and no browser.

**Consequence:** the second authoring path means two places to look for a model, so the rules that make them interchangeable are explicit and checked: **metres, base at y = 0, flat-shaded, ≤700 tris, deterministic, three or four tones** — a placement can swap between a GLB and a kit model without moving, which is exactly what the fallback does at runtime. Vertex colours are written **linear** and converted once for display (`ColorManagement` already treats a hex as sRGB — converting twice is how a rock ends up black, which is what this caught). The kit's `Group`s are per-consumer and its geometry and materials are shared and cached, mirroring the GLB path's `clone(true)`. And the honest gap: **nothing here proves the garden looks right on a real GPU**, so the device pass stays the user's — the sheet is a review aid, not a substitute for one.

## ADR-023 · Sentinel: the second networked feature, and the one that says what it cannot prove
**Decision:** Devlofy gains its second new **category** since v0.1 — **Sentinel**, the board that answers "is anything of mine down?" — and it is the app's **second networked feature**. It reaches the network under rules that are stricter than GitHub's, because it is the first feature whose *purpose* is to make requests, and those requests go to the user's own infrastructure:
1. **The app checks when you look, and only then.** There is no polling daemon, no background task and no scheduler. Checks run when the board opens *if* the newest check is older than `STALE_AFTER_MS` (15 minutes), and whenever the user presses Check all / Check now. Every row therefore shows the time it was measured, and every figure on the screen is labelled with what it is over. This is why there is no live dot anywhere in Sentinel: nothing about it is live.
2. **A check is a record; an incident is a view.** The `verdict` is computed once, at the moment the check is taken, from the expectations set at that moment, and stored — changing a target's expected status tomorrow must not rewrite what yesterday's checks meant (the same reason ADR-017 keeps an invoice a view *over* sessions, seen from the other side). Incidents then go the other way: "three failures in a row" is *derived* from the stored verdicts by `incidentsIn()`, so the rule is a pure function that can be improved without a migration.
3. **User content goes in SQLite; measurements are pruned, not tombstoned.** Migration **v4** adds `watch_sites` (a target: name, URL, expected status, time budget, paused flag, note) and `watch_checks` (one measurement: verdict, status, ms, source, detail). `watch_sites` is user content and is tombstoned like every other table; `watch_checks` is deliberately the **one table with no `deleted_at`** — a check is a measurement the app took, not a document the user wrote, so it is pruned to the newest 500 per target at every write and deleted outright with its target, which keeps the log and the export bounded. Unlike GitHub's snapshot (ADR-011/ADR-019), none of this is someone else's data: it is the user's own history, so it belongs in the database and in the JSON export (`version: 3`).
4. **The two runtimes are allowed to prove different things, and the UI says which.** `src/lib/sentinel/probe.ts` (native) reads the real HTTP status, headers and timing; `probe.web.ts` cannot — a browser hides every cross-origin response behind an opaque one — so it issues `mode: 'no-cors'` and reports only that *something answered* and how long it took. The verdict vocabulary follows the evidence rather than flattering it: a web result is labelled **reachable**, never "up", because `verdictFor()` refuses to call a target down on evidence it does not have, and the board prints a sentence explaining the limit whenever the numbers on screen came from a browser. Status colour follows the same three roles the rest of the app uses — **up reads in `accent`, slow in `ember`** (a verdict about *time*, which is what ember is for), **down in `danger`** — so no fourth hue enters the palette.
5. **Checks run one at a time, on purpose.** `checkSites()` is sequential: ten simultaneous requests contend for the same radio, which inflates exactly the number this feature exists to report.
6. **One promise the app refuses to fake:** "uptime" counts the checks that were taken, never wall-clock time. A board that watches only while you are looking would turn a minute-by-minute percentage into a lie, so the figure is always shown with its denominator ("99.4% up · 12 checks") and the empty incident state says absence of evidence is not proof.

**Why:** it collapses a whole SaaS category (Pingdom, Better Stack, UptimeRobot) into one offline-first board, and it is the most **Garden**-like idea left in [[10-categories]]: a living board that is worth more every week you keep using it, made of the user's own targets rather than a vendor's dashboard. It also passes the platform test that killed other candidates — it is Tier A (HTTPS + `fetch`) and needs no new dependency. The category rule (ADR-001) is satisfied the same way Bench satisfied it: it is reached from a shelf in **More** (`networked` section → `/sentinel`), not by displacing a tab.

**Consequence:** ADR-019's framing — "GitHub is the *only* screen in the app that needs the network" — is superseded; the accurate statement is now that **GitHub and Sentinel are the only networked features, and each has its own rule for the network it touches** (GitHub: someone else's API, snapshot in KV, writes branch-bounded by ADR-020; Sentinel: the user's own URLs, records in SQLite, requests only on demand, nothing written anywhere remote). Every other promise still holds: no backend, no account, no cloud AI (ADR-002); `searchEverything()` grows a **fifth** kind (`site`) because a watched target is content the user wrote and search must not have a dead spot; and `exportAll()` carries both new tables in the same change that creates them. What Sentinel cannot do is stated rather than hidden: no background checking (so no honest "was it up at 03:00?"), no status codes or bodies on web, no notification when something goes down while the app is closed — each of those needs either a development build with a background task, a proxy the app does not have, or a server the product does not want, and each is in [[08-backlog]] with that reason attached. Sentinel extends the known-answer habit with a **second** self-check file (`src/lib/sentinel/self-check.ts`, 78 assertions over verdicts, windows, incidents, latency and URL parsing) rather than growing Bench's, so each folder's checks stay runnable on their own.
